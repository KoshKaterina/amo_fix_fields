# Самоисцеление сделок amgroup без контакта: выкат и откат

Ветка `feat/amgroup-contact-heal`, подготовлено 21.10.2026. **На прод не выкачено**: выкат,
правка `.env` и пересоздание контейнера идут только по отдельному «го» Кати.

## Зачем

20–21.10.2026 шесть сделок по заказам сайта остались без контакта (36583137, 36583153,
36583813, 36583847, 36583849, 36583851). amgroup создаёт контакт, потом сделку, потом привязку.
Все шесть сбоев пришлись на утренние окна, когда API amo отдавал 500, таймауты и 429. Шаг
«привязать» у amgroup упал и не повторился. Без контакта офис не может создать накладную СДЭК.
Разбор есть в `projects/amo-cleanup/JOURNAL.md` рабочей папки, записи от 20 и 21.10.

## Что делает

Модуль `amgroup_contact_heal.py`. Сделку он берёт, когда выполнены все условия:

- «Заказ создан» = «Из МойСклад» (поле 576683, enum 1040195);
- заполнен «ID Контрагента» (поле 576695);
- контакта нет;
- сделка открыта;
- сделка старше `AMGROUP_CONTACT_HEAL_MIN_AGE_MIN` (5 мин).

1. Контрагент МС по ID → телефон и почта → поиск контакта в amo (`/contacts?query=`).
   Совпадение сверяется по значению поля: телефон по последним 10 цифрам, почта без учёта
   регистра.
2. **Кандидат ровно один** → сделка перечитывается (вдруг amgroup успел) → `POST /leads/{id}/link`
   с `is_main: true` → проверка чтением → примечание «Контакт привязан автоматически…» → повторный
   заход распределения (`process_lead_distribution`, он идемпотентен).
3. **Ноль или несколько кандидатов**, либо у контрагента нет ни телефона, ни почты → контакт
   **не создаётся**. В сделку пишется примечание, в тех.чат уходит один алерт с id сделки и
   кандидатов, без имени и телефона клиента.
4. **amo или МС не ответили** (5xx, таймаут, 429, открытый предохранитель): исход «не знаю».
   Модуль ничего не пишет и никого не зовёт, сделка повторится на следующем проходе.

Модуль срабатывает двумя путями:

- **фоновый проход** раз в 3 минуты по сделкам, созданным за 24 часа. Он ловит и сделки вне
  профилей распределения;
- **отложенный вызов из `lead_distribution._contact_wait_loop`**. Когда распределение не
  дождалось контакта, модуль выжидает свой порог и пробует привязать. Если amgroup за это время
  привязал контакт сам, распределение тоже зовётся заново: раньше такая сделка оставалась
  без ответственного.

Повторных алертов не будет: завершённые исходы хранятся в `/app/var/amgroup_contact_heal.json`.
Исходы «не знаю» туда не записываются.

## Флаги (`waybill_config.py`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `AMGROUP_CONTACT_HEAL_ENABLED` | `0` | без неё модуль не поднимает цикл, вызов из распределения тоже пустой |
| `AMGROUP_CONTACT_HEAL_DRY_RUN` | `1` | всё читает и решает, но только пишет в лог «привязали бы…»; ни привязки, ни примечаний, ни алертов, ни состояния |
| `AMGROUP_CONTACT_HEAL_MIN_AGE_MIN` | `5` | сколько ждём amgroup (в норме он привязывает за 2–5 с, при тормозах было 16 с) |
| `AMGROUP_CONTACT_HEAL_INTERVAL_SEC` | `180` | интервал фонового прохода |
| `AMGROUP_CONTACT_HEAL_LOOKBACK_H` | `24` | окно фонового прохода по времени создания сделки |
| `AMGROUP_CONTACT_HEAL_STATE_PATH` | `/app/var/amgroup_contact_heal.json` | файл состояния |

### Порядок (по «го» Кати, один шаг за раз)

1. `LOCKS.md`: занять выкатку amo-fix-fields.
2. **Сверка по md5** четырёх изменённых файлов с `/opt/integrations/amo_fix_fields/`. Сверять
   нужно с `origin/master` на `1c8d058`, не с веткой; CRLF расхождением не считается.
   ⚠️ Прод бывает впереди master, особенно по `lead_distribution.py`. Если файл на сервере
   отличается, ветку не заливать: перенести её правку в серверную версию и сверить ещё раз.
3. Снять резервную копию пяти файлов на сервере (`*.bak-20261021`, или рядом с датой выката).
4. `rsync` пяти файлов.
5. Этап 1, сухой режим: в `.env` записать `AMGROUP_CONTACT_HEAL_ENABLED=1`,
   `AMGROUP_CONTACT_HEAL_DRY_RUN` не трогать (умолчание `1`). Затем `docker compose build && up -d`.
   ⚠️ Пересборка роняет вебхуки amo в 502, см. `knowledge/vebhuki-teryayutsya-pri-peresborke-amo-fix-fields.md`.
6. Смоук контура: `scripts/ops/smoke_amo_contour.sh`. В логе должно быть
   `amgroup_contact_heal запущен: … режим сухой`.
7. Сутки-двое наблюдения: `docker logs amo-fix-fields 2>&1 | grep amgroup_contact_heal`. Смотрим:
   - сколько сделок «без контакта» на проход. Ожидается 0, изредка единицы. Если там десятки
     заказных сделок, значит выборка списком не отдаёт `_embedded.contacts`, и этап 2 не
     включать (см. «Непроверенное»);
   - что решил модуль по каждой («привязали бы контакт N», «позвали бы человека…»). Сверить
     руками хотя бы один случай.
8. Этап 2, боевой режим: `AMGROUP_CONTACT_HEAL_DRY_RUN=0`, пересоздать контейнер, ещё раз
   смоук. Снять лок.
9. Коммит в организацию: слить ветку в master в тот же заход (правило `AGENTS.md`).

## Откат

- **Быстрый, без кода:** `AMGROUP_CONTACT_HEAL_ENABLED=0` в `.env`, затем пересоздать контейнер.
  Цикл не поднимется, вызов из распределения станет пустым. Остальной код работает как раньше.
- **Полный:** вернуть пять файлов из `*.bak`, `docker compose build && up -d`, смоук. Файл
  `/app/var/amgroup_contact_heal.json` можно оставить, без модуля его никто не читает.
- **Сделанные привязки сами не откатываются.** Их список: `grep "amgroup_contact_heal .*: linked"`
  в логе, плюс ключи с `"outcome": "linked"` в файле состояния. В каждой такой сделке есть
  примечание «Контакт привязан автоматически…» со ссылкой на контакт. Отвязать можно руками
  в карточке или `POST /api/v4/leads/{id}/unlink` (только по «го»).

  шум полнотекстового поиска; amgroup привязал до нас, пока мы искали, одновременно с нами,

  `test_lead_distribution.py` даёт 95 из 95 (тесты запускать через
  `repositories/amo_fix_fields/.venv`, в нём есть `aiogram`).
- **Против живого amo не проверялось.** Непроверенное:
  - отдаёт ли `GET /api/v4/leads?filter[created_at]…&with=contacts` у списка
    `_embedded.contacts`. По документации amo v4 отдаёт. Если нет, фоновый проход примет все
    заказные сделки за «без контакта». Вреда не будет, потому что `heal_lead` сам перечитывает
    сделку и увидит контакт, но запросов станет больше. Сухой режим это покажет;
  - находит ли `query=<цифры>` контакт, у которого номер записан через 8. Тот же приём уже
    работает в `amgroup_lead_builder`. Если телефон не найдётся, остаётся почта, а иначе
    будет алерт «не найден», без вреда.
- **Событие алерта `amgroup_contact_heal` в каталоге панели не заведено.** Пока его нет,
  `alerts.decide` отдаёт старый путь, то есть основной тех.чат (`TG_ALLOWED_CHAT_ID`).
  Завести событие в team-panel можно отдельной задачей.

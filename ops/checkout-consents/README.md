# Checkout → МойСклад → существующие поля контакта amoCRM

`checkout_consent_sync.py` — самостоятельный процесс поверх существующих клиентов
контейнера amo-fix-fields. Публичных маршрутов нет, обработчики вебхуков не меняются.
По умолчанию выполняет только чтение. Запись разрешает только явный `--apply`.

## Данные

Поле заказа покупателя МС «Согласия с сайта» (text):
`327bfdfa-cbd4-11f1-0a80-1c9d00f0e1bf`. Строка версии
`checkout-marketing-v1-2026-10-19` содержит ПДн, рекламу по четырём каналам,
исходное время с часовым поясом и версии. Email идёт прежним отдельным полем.
Исторические согласия только на email этот обработчик не расширяет.

Известные существующие поля **контакта**, все text:

| Назначение | Согласие | Версия | Дата |
|---|---|---|---|
| ПДн | 578239 | 578241 | 578279 |
| Реклама | 578245 | 578247 | 578277 |

Ни одно новое поле CRM не создаётся. Удалённое поле сделки578315 не используется.
Поля согласия получают принятый формат `Да`; даты — ISO8601 с точностью до секунды

Отсутствие отметки рекламы в новом заказе оставляет рекламные поля контакта прежними;
это не отзыв ранее выданного согласия. Выбор заказа остаётся в Woo/МС.

## Связь и свежесть

Сканируются ограниченные окна изменения заказов МС с перекрытием. Полный UUID заказа
должен точно совпасть с существующим полем сделки FIELD_MOYSKLAD_ORDER_UUID (576689).
Из сделки берётся один главный контакт либо единственный контакт. Дубли сделок с
разными контактами и неоднозначные связи требуют разбора; создание сущностей запрещено.

До PATCH проверяются исходная дата и история изменений соответствующих полей контакта,
затем контакт перечитывается. Более поздний выбор, дата с точностью до дня в тот же день,
неизвестные/искажённые даты и история очистки полей защищены от перезаписи. Пропуски
из-за неполных старых дат требуют отдельного решения, а не автоматического проставления.
У API здесь нет атомарного сравнения версии контакта перед PATCH: перечитывание и история
сужают окно гонки с другими писателями, но не исключают его полностью. Расхождение при
проверке результата паркуется; автоматической компенсации чужих значений нет.

## Устойчивость

SQLite хранит курсор и очередь: опоздавшая сделка amgroup не теряет согласие.
До PATCH сохраняется intent; повторного PATCH после неизвестного результата нет.
Следующий проход только читает контакт: совпадение с намерением завершает запись,
остальное остаётся parked для разбора. Один владелец apply-ledger защищён flock.
Повторная доставка того же снимка не включает подписку заново после ручной отписки.
Ожидающие записи обслуживаются по очереди попыток, чтобы одна потерянная связь
не блокировала остальные. Курсор продвигается только после полного успешного окна.
Лимит страницы/окна не означает «заказов больше нет»: при неполном ответе курсор сохраняется.

## Подготовленный запуск, пока НЕ активирован

Установить исходный файл в `/opt/integrations/amo_fix_fields/checkout_consent_sync.py`;
юниты из этой папки — в /etc/systemd/system. Код передаётся отдельному python-процессу
в контейнере через stdin, поэтому пересборка/перезапуск amo-fix-fields не требуется.
Ключи остаются у существующих клиентов; новые env-файлы и доступы не нужны.

Dry-run: передать тот же файл в `docker exec -i -w /app amo-fix-fields python - --since <ISO-время-с-поясом>`.
Без `--apply` ledger существует только в памяти и не потребляет очередь будущего запуска.

Apply-unit запускается каждые2мин; состояние `/app/var/checkout-consents.sqlite3` лежит
в существующем persistent var. `--since now` используется только при первом запуске:
исторической массовой заливки нет. Начать worker до включения нового producer сайта/склада.
Код сайта и Woo→МС — отдельные подготовленные изменения; без их выпуска живой путь не готов.

## Откат

Остановить и выключить только `sunscrypt-checkout-consents.timer` и его service.
Сам контейнер и остальные таймеры не трогать. SQLite сохранить вместе с parked-записями:
удаление ledger может привести к повторной обработке исторического выбора.
Автоматически возвращать значения контакта нельзя: за это время мог появиться новый выбор.
Перед выпуском сохранить текущие файлы/хэши всех трёх частей. Для Woo→МС потребуется
отдельно согласованный рестарт только woocommerce-sklad; сайт сначала прошёл staging.
